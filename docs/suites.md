# Suites, checks and sub-checks

Meerkat has three levels. Each level is one idea.

| Level | What it is | Example | You can |
|---|---|---|---|
| **Suite** | The general check you pick. A short list of related checks. | `secrets`, `web-security`, `accessibility` | run it, turn it off, read its purpose |
| **Check** | One script or tool run, with its own log, exit code and time. | `secret-scan`, `eslint` | run it, turn it off, read its log |
| **Sub-check** | One rule inside a check, reported on its own: pass, fail or not applicable. | `secret-scan/aws-access-key` | run it, turn it off, see its reason |

`meerkat suite list` shows the suites, `meerkat suite show <name>` one suite. The suites come from `lib/suites.mjs`: a check finds its suite by its own `suite` field, else by its id, else by the pack it came from. A check that matches none is shown under `other`, never lost.

## Running and selecting

| You type | It runs |
|---|---|
| `meerkat check secrets` | every check of the suite |
| `meerkat check secrets/secret-scan` | one check (it must be in that suite) |
| `meerkat check secrets/secret-scan/aws-access-key` | the check, then reports only that sub-check |
| `meerkat check secret-scan` | one check by its id, as before |
| `meerkat verify --suite secrets,web-security` | the checks of these suites; `--only` takes the same words |

A suite run does not look at the tier: you asked for the suite, so its quick and slow checks both run (opt-in checks, such as the AI review, only with `--include ai`). The menu's "Choose checks one by one" shows about fifty suites instead of every check: Space ticks a whole suite, Right opens it so you can tick single checks, Enter runs.

## Turning things off

In `meerkat.config.json`:

```json
{
  "disable": ["eslint", "suite:web-security"],
  "disableSubs": ["secret-scan/aws-access-key"]
}
```

- `"suite:<name>"` in `disable` turns off every check of a suite. Every run lists them as `[DISABLED]`.
- `disableSubs` turns off single rules, as `check/sub` (or `suite/check/sub`). A turned-off rule is left out of the counts. If a check exits with an error and every rule that failed is turned off, the check passes; if a different rule failed too, it still fails.
- A mistake (a bad name, an unknown suite or check) is reported as a note on every run and the rest of the file still applies.

## How counting works

- The headline is `249 checks (1032 sub-checks: 1010 passed, 3 failed, 19 not applicable here)`. Not applicable is its own result and **never** counts as a failure.
- A check that prints no sub lines counts as **one** sub-check (the check itself), so every total adds up. A check that could not run (`NOT RUN`) counts as one not-applicable sub-check.
- `meerkat suite list` keeps two numbers apart: the **catalogue** (everything Meerkat ships) and what **applies here** (the packs that are on for this folder, minus what the config turned off). The README block is generated by `node tools/gen-checks.mjs`.
- A check can declare how many rules it reports with `subs: <1..500>` in its definition. That is only used for the catalogue count and the board before the check has run; the real count of a finished run is what the check printed.

## Writing sub-check lines (for check authors)

Print one line per rule to **stdout**, exactly:

```
MEERKAT-SUB <PASS|FAIL|NA> <rule-id> <short reason>
```

- `rule-id`: lowercase letters, digits and dashes, 1 to 61 characters (`/^[a-z0-9][a-z0-9-]{0,60}$/`).
- reason: optional, at most 200 characters, control characters are removed.
- Anything else that starts with `MEERKAT-SUB` is dropped. The first line of each rule id wins; at most 2000 rules per check.
- The runner takes these lines out of the output (like `MEERKAT-FILE`): they never reach the board's "last line" or the saved output. They are written into the check's log under `--- sub-checks ---`, and into `summary.json` as `subs`.
- The **exit code still decides** the check. If the script exits 0 but printed a `FAIL` line, the check is marked FAIL with `sub-check <id> failed` (a script that says both is a bug). If it exits 1 with no `FAIL` line, nothing changes. A `FAIL` line also becomes the reason shown for a failed check.

A tiny script:

```js
// scan.mjs, run as { cmd: 'node', args: ['scan.mjs'] }
import { readFileSync } from 'node:fs'
const rules = [
  ['no-eval', (src) => !/\beval\(/.test(src), 'eval() found'],
  ['no-debugger', (src) => !/\bdebugger\b/.test(src), 'debugger statement found'],
]
const src = readFileSync('app.js', 'utf8')
let failed = false
for (const [id, ok, why] of rules) {
  console.log(ok(src) ? `MEERKAT-SUB PASS ${id}` : `MEERKAT-SUB FAIL ${id} ${why}`)
  failed ||= !ok(src)
}
console.log('MEERKAT-SUB NA no-eval-in-workers no worker files here')
process.exit(failed ? 1 : 0)
```

A check written as a JavaScript function may return `subs: [{ id, status, reason }]` next to `ok` and `detail`; they are judged the same way.

## Where the sub-checks show

- the end list: `SUMMARY [ 0:41 ] 249 checks (1032 sub-checks: ...)`, and one `SUITE` line per suite with its checks and sub-checks (above 24 checks; `--flat` shows every check);
- the live board: one line per suite, opened for failures and running checks, with the suite's sub-check count;
- `report.md`: a "Suites" table and every failed sub-check with the command to run it again;
- `summary.json`: `suite`, `subs`, `subTotal`, `subPass`, `subFail`, `subNa` on each result, `subTotals` and `suites` for the run; `timeline.jsonl` end events carry `subs` counts.
